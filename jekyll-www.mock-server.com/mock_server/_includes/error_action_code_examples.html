The bytes are sent to the client exactly as given, in place of a response: they do not have to be a valid or complete HTTP response, which is useful for testing how a client copes with a corrupt or truncated reply. A client that reaches MockServer through its CONNECT or SOCKS proxy receives the same bytes as a client connected directly. Without dropConnection the connection is left open after the bytes, and is closed later like any other idle connection. A later request on that connection is answered as usual, for its own method: a GET sent after a HEAD that was answered with raw bytes still receives its body.

Raw bytes can only be sent over HTTP/1.1. A request that arrives over HTTP/2 is sent no bytes: its stream is left open with no response, or, with dropConnection, that stream alone is reset and the connection stays open. To reset an HTTP/2 or HTTP/3 stream with a chosen error code use streamError, below.

Use resetConnection to answer a matched request with a TCP reset instead of a response. The client sees "connection reset by peer" (ECONNRESET), where dropConnection closes the connection cleanly and the client sees the end of the stream. Use it to test how a client handles a server, proxy or load balancer that aborts a connection.

  • HTTP/1.1 and TLS: the connection is reset. Over TLS no TLS close message is sent first, just as with a real reset.
  • HTTP/2: the whole TCP connection is reset, so every other request in progress on it fails too. To reset only the matched request use streamError, which sends an HTTP/2 RST_STREAM.
  • HTTP/3: QUIC runs over UDP, which has no reset, so the QUIC connection is closed at once with the H3_INTERNAL_ERROR error code.
  • Through MockServer's proxy (an HTTPS CONNECT tunnel or SOCKS, over HTTP/1.1, TLS or HTTP/2): the client's own connection to MockServer is reset.

resetConnection takes precedence over streamError and dropConnection. If responseBytes are also set they are written first, but the reset discards anything the client has not yet received, so they may not arrive. Like every error action, it is not supported when MockServer is deployed as a WAR. A WireMock CONNECTION_RESET_BY_PEER fault is imported as resetConnection.

new MockServerClient("localhost", 1080)

Use respondBeforeBody on the request matcher to dispatch the configured response before MockServer reads the request body. The matcher must not include a body matcher and only RESPONSE and ERROR actions are supported. The connection is always closed after the response (the inbound body has not been consumed, so reuse is unsafe), so any closeSocket value is ignored, and the response carries a Connection: close header unless you set keepAliveOverride or suppressConnectionHeader. MockServer keeps reading and discarding the rest of the body for up to 5 seconds after responding, so a client that sends its whole body before reading the response still receives it, provided it finishes sending within that time. HTTP/1.1 only — HTTP/2 connections fall through to the standard pipeline. This is useful for reproducing client behaviour when a server responds and closes mid-upload.

new MockServerClient("localhost", 1080)

            .withStatusCode(403)
            .withBody("forbidden")
            .withConnectionOptions(
                connectionOptions().withKeepAliveOverride(false)

For resilience testing of clients that must cope with mid-stream resets, an error action can reset just the matched request stream instead of returning a response. Set streamError to the stream error code to send: over HTTP/2 MockServer sends an RST_STREAM for that stream (RFC 7540 codes, e.g. REFUSED_STREAM = 7), and over HTTP/3 a QUIC RESET_STREAM (RFC 9114 codes, e.g. H3_REQUEST_CANCELLED = 268 / 0x10c). Other streams multiplexed on the same connection are unaffected.

HTTP/1.1 caveat: HTTP/1.1 has no stream concept, so a request that matches over HTTP/1.1 cannot be reset at the stream level — MockServer instead drops the whole connection (the same behaviour as dropConnection).

Precedence: if both streamError and dropConnection are set on the same error action, streamError wins and dropConnection is ignored (over HTTP/1.1 the stream-error fallback drops the connection anyway).

HTTP/2NO_ERROR0
HTTP/2PROTOCOL_ERROR1
HTTP/2INTERNAL_ERROR2
HTTP/2REFUSED_STREAM7
HTTP/2CANCEL8
HTTP/2ENHANCE_YOUR_CALM11
HTTP/2HTTP_1_1_REQUIRED13
HTTP/3H3_REQUEST_REJECTED267 (0x10b)
HTTP/3H3_REQUEST_CANCELLED268 (0x10c)
HTTP/3H3_INTERNAL_ERROR258 (0x102)
