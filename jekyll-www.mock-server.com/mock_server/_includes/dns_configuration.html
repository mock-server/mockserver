DNS Configuration:

Enable or disable the DNS mock server. When enabled, MockServer starts a UDP DNS server that matches incoming DNS queries against expectations. DNS expectations use DnsRequestDefinition for matching and DnsResponse for responses. Supported record types: A, AAAA, CNAME, MX, SRV, TXT, PTR.

If DNS mocking is enabled and MockServer cannot open its DNS port, MockServer does not start. Earlier versions logged the warning exception binding DNS port - DNS mocking disabled and started without DNS, so a deployment in that state looked healthy while answering no DNS queries.

Type: boolean Default: false

Java Code:

ConfigurationProperties.dnsEnabled(boolean enable)

System Property:

-Dmockserver.dnsEnabled=...

Environment Variable:

MOCKSERVER_DNS_ENABLED=...

Property File:

mockserver.dnsEnabled=...

Example:

-Dmockserver.dnsEnabled="true"

The UDP port for the DNS mock server. Set to 0 to let MockServer choose a free port; it passes over a port another application already uses, so queries to the chosen port on 127.0.0.1 reach MockServer. The port it chose can be read:

  • from ClientAndServer.getDnsPort() or MockServer.getDnsPort();
  • in a JUnit 4 test from MockServerRule.getDnsPort(), and in a JUnit 5 test from the ClientAndServer the MockServerExtension injects;
  • in a Spring test from the ${mockServerDnsPort} placeholder or a field annotated @MockServerDnsPort (turn DNS mocking on with @MockServerTest("mockserver.dnsEnabled=true"));
  • from the dnsPort field of the answer to PUT /mockserver/status, for example {"ports":[1080],"dnsPort":53053,...}, which leaves the field out while DNS mocking is off;
  • from the start-up log line DNS mock server started on port: ....

The getDnsPort() methods, the placeholder and the annotated field give -1 while DNS mocking is off. The JUnit 4 rule and the JUnit 5 extension start MockServer with DNS mocking on when mockserver.dnsEnabled is set to true as a system property, environment variable or in mockserver.properties; a JUnit 5 test can instead register new MockServerExtension(ClientAndServer.startClientAndServer(configuration().dnsEnabled(true))) with @RegisterExtension.

The DNS port listens on the address set by Local Bound IP, as the HTTP(S) ports do, or on every address when that is not set.

This setting is only used when DNS mocking is enabled. If MockServer cannot open the port, it does not start: it closes the HTTP and HTTPS ports it had already opened and reports one line naming the port and the cause, for example:

DNS mocking is enabled (dnsEnabled=true, dnsPort=5353) but UDP port 5353 could not be opened or bound, so MockServer cannot start: free the port if another application holds it, choose a different dnsPort (0 picks a free port, and a port below 1024 can need extra privileges), or set dnsEnabled=false to run without DNS mocking (underlying error: BindException: Address already in use)

The text after underlying error: is the error as the platform reports it, so its exact wording varies between operating systems; look in it for Address already in use or Permission denied.

The usual causes are:

  • Another application is using the port. On port 53 that is often the host's own resolver (for example systemd-resolved or dnsmasq); port 5353 belongs to mDNS and is normally already in use on macOS, and on Linux hosts that run Avahi. On macOS this includes an application that listens on the port for IPv4 only (0.0.0.0): the operating system would let MockServer open the port too, but queries sent to 127.0.0.1 would then go to that application, so MockServer refuses the port, and the underlying error names the conflict and gives an lsof command that finds the application.
  • Another MockServer was started with the same dnsPort: two embedded servers in one JVM, test forks running in parallel that share one mockserver.dnsPort system property or properties file, or several instances on one host started from the same configuration. Earlier versions let the first one serve DNS while the others quietly served none; now every one but the first fails to start. Give each instance its own port, or use 0.
  • The process is not allowed to use the port (the underlying error is Permission denied): on Linux a port below 1024, such as 53, can only be used by root, unless net.ipv4.ip_unprivileged_port_start allows it. The MockServer Docker image runs as a non-root user, so this happens with --network host or wherever that setting is 1024 (Docker itself sets it to 0 inside a container, so port 53 normally works there). For a port below 1024 the message says so and lists the fixes: choose a port of 1024 or above and publish it as the port you want (for example -p 53:5053/udp with dnsPort=5053), run MockServer as root (--user 0), or lower that setting (--sysctl net.ipv4.ip_unprivileged_port_start=53). Adding the NET_BIND_SERVICE capability with --cap-add does not help: Docker does not give it to a non-root user.

What you see depends on how you run MockServer:

  • Command line, Docker and Helm — the process exits with a non-zero status after printing that line, so a container stops (and under Kubernetes restarts and reports CrashLoopBackOff) instead of running without DNS. Read the container log for the line. A dnsPort that is not a port number (for example above 65535) fails in the same way; the line then reads its server could not start on UDP port ... and is followed by a stack trace.
  • Embedded in a JVM (ClientAndServer.startClientAndServer(...), new MockServer(...), the JUnit 4 rule, the JUnit 5 extension and the Spring test listener) — the start throws a RuntimeException (org.mockserver.netty.dns.DnsStartupException) carrying that message and the original error as its cause, as an HTTP port that is already in use does.
  • Maven plugin and Spring Boot starter — the plugin's start, run and runForked goals fail the build with that message, and the mockserver-spring-boot-starter fails the application context's start-up (a BeanCreationException whose cause is the exception above).

To run without DNS mocking, set dnsEnabled to false (the default).

Type: integer Default: 0

Java Code:

ConfigurationProperties.dnsPort(int port)

System Property:

-Dmockserver.dnsPort=...

Environment Variable:

MOCKSERVER_DNS_PORT=...

Property File:

mockserver.dnsPort=...

Example:

-Dmockserver.dnsPort="5053"

The DNS mock listens on UDP only. A DNS response that does not fit the client's UDP payload limit is sent truncated, with the TC ("truncated") flag set, carrying as many complete records as fit. The limit is 512 bytes, or the larger buffer size the client advertises if it uses EDNS(0) — most modern resolvers advertise 4096.

Standard resolvers respond to the TC flag by retrying the query over TCP. Because MockServer does not currently serve DNS over TCP, that retry has nowhere to go. If you need to return many records, keep the response under the limit or make sure your client uses EDNS(0).

TXT values longer than 255 bytes are split across multiple character-strings, as RFC 1035 requires; resolvers rejoin them, so a long value such as a DKIM key is delivered intact.

A record that cannot be encoded as valid DNS — an unparseable IP address, an A record given an IPv6 value, a name label longer than 63 bytes, or a name longer than 255 bytes — causes the query to be answered with SERVFAIL, and the reason is logged. This is deliberate: returning a successful-looking response built from unencodable configuration would hide the mistake.
