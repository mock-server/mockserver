When you test an application that calls an LLM, you face two problems: the real API is slow, costs money, and returns different results every run. MockServer solves both: tell it which provider your application targets and what the completion should contain, and it returns a byte-for-byte correct response — including the full streaming SSE framing — without touching the network.

In practice: point your application at MockServer instead of api.openai.com (or the equivalent endpoint for your provider), create one expectation, and your test gets a deterministic, instant, free LLM response every time. 

# Start MockServer
docker run -d --rm -p 1080:1080 mockserver/mockserver

# Create an OpenAI-compatible completion mock
curl -s -X PUT http://localhost:1080/mockserver/expectation \
  -H "Content-Type: application/json" \
  -d '{
    "httpRequest":  { "method": "POST", "path": "/v1/chat/completions" },
    "httpLlmResponse": {
      "provider": "OPENAI",
      "model": "gpt-4o",
      "completion": {
        "text": "MockServer is a free, open-source HTTP mock server.",
        "stopReason": "stop",
        "usage": { "inputTokens": 12, "outputTokens": 9 }
      }
    }
  }'

# Your application can now call http://localhost:1080/v1/chat/completions
# and receive a correctly formatted OpenAI response.

MockServer can mock LLM API responses from any major provider using the httpLlmResponse action. You describe the completion in a provider-neutral format and MockServer encodes it into the correct wire format for the target provider — headers, JSON structure, streaming framing, and all. Basic Completion Mock

Create an expectation with an httpLlmResponse action. The provider tells MockServer which wire format to produce; the completion describes what to return.

The Java client has a typed fluent API (LlmMockBuilder + HttpLlmResponse). All other clients send the expectation as raw JSON using their generic expectation method (mockAnyResponse in JavaScript; a direct PUT to /mockserver/expectation in other languages). 

import static org.mockserver.client.LlmMockBuilder.llmMock;
import static org.mockserver.model.Completion.completion;
import static org.mockserver.model.Provider.OPENAI;
import static org.mockserver.model.Usage.usage;

// OpenAI — POST /v1/chat/completions
llmMock("/v1/chat/completions")
    .withProvider(OPENAI)
    .withModel("gpt-4o")
    .respondingWith(
        completion()
            .withText("MockServer is an open-source HTTP mock server.")
            .withStopReason("stop")
            .withUsage(usage().withInputTokens(12).withOutputTokens(8))
    )
    .applyTo(mockServerClient);
var mockServerClient = require('mockserver-client').mockServerClient;

// OpenAI — POST /v1/chat/completions

    "httpRequest": {

            "text": "MockServer is an open-source HTTP mock server.",
            "stopReason": "stop",

        }
    }
}).then(
    function () { console.log("expectation created"); },
    function (error) { console.log(error); }
);

When a request matches POST /v1/chat/completions, MockServer returns an OpenAI-formatted JSON response with the specified text, model, stop reason, and token usage — including the correct id, created, and object fields that the OpenAI SDK expects.

A stopReason is converted to the value each provider uses, so you can share one expectation across providers. For example, length becomes max_tokens for Anthropic and Bedrock InvokeModel, MAX_TOKENS for Gemini, and done_reason: "length" for Ollama; stop becomes end_turn for Anthropic. Ollama's final message always has a done_reason: stop unless you set a max-tokens value. When an Ollama reply is streamed, its tool calls arrive in a message before that final one, as Ollama sends them, and the final message holds only the stop reason and token counts.

OPENROUTER reports two values on each choice, as OpenRouter does: finish_reason, normalised to stop, length, tool_calls or content_filter, and native_finish_reason, the raw value of the model behind it. Set stopReason to that model's own value to mock it: with STOP (a Gemini model) or end_turn (a Claude model) a choice has "finish_reason": "stop" and that value as its native_finish_reason. Without a stopReason both fields have the same value. In a stream, native_finish_reason is null until the chunk that carries the finish_reason.

AWS Bedrock: Converse and InvokeModel

AWS Bedrock has two APIs that return different JSON, and BEDROCK supports both. MockServer picks the format from the path of the incoming request, so the same expectation works with whichever API your code calls:

Request path ends withResponse format
/converse Converse API: {"output":{"message":{"role":"assistant","content":[{"text":"..."}]}},"stopReason":"end_turn","usage":{"inputTokens":5,"outputTokens":5,"totalTokens":10},"metrics":{"latencyMs":0}}. The same format for every model (Claude, Titan, Nova, Llama, …). Tool calls are {"toolUse":{"toolUseId":"...","name":"...","input":{...}}} content blocks.
/converse-stream ConverseStream: binary AWS event-stream (application/vnd.amazon.eventstream) carrying messageStart, contentBlockStart (tool calls only), contentBlockDelta, contentBlockStop, messageStop and a final metadata event with usage and metrics. Each event's JSON is sent as-is, the way AWS sends it.
/invoke InvokeModel for Anthropic Claude: the Anthropic Messages body (content[], stop_reason, usage.input_tokens / output_tokens).
/invoke-with-response-stream InvokeModelWithResponseStream: binary AWS event-stream where each chunk event wraps an Anthropic streaming event as {"bytes":"<base64>"}.

If the path doesn't end with one of these (for example, a gateway path), MockServer looks at the request body instead. A Converse-style body (content blocks such as {"text":"..."}, or an inferenceConfig or toolConfig field) gets the Converse format. Anything else gets the InvokeModel format, which is what BEDROCK returned before Converse support was added. For streaming, set "streaming": true on the completion, just as for other providers.

In the Converse format, totalTokens is inputTokens + outputTokens, plus cachedInputTokens and cacheCreationTokens if you set them. Those two appear in the response as cacheReadInputTokens and cacheWriteInputTokens. This follows AWS, where inputTokens counts only the input tokens that weren't read from or written to the cache. metrics.latencyMs is always 0; use streaming physics or a response delay to simulate latency. Conversation matchers read Converse requests too: the system text blocks, the messages[].content[] text, image, toolUse and toolResult blocks. Any stopReason you set is converted to one of the values AWS accepts, so AWS SDKs can always read it. For example, refusal becomes content_filtered, and unrecognised values become end_turn.

Chaos follows the API too. A contentFilterBlockProbability block on a Converse request returns a Converse response with stopReason content_filtered; on InvokeModel it returns the Anthropic refusal (stop_reason refusal with a stop_details object). Injected errors and structured-output enforcement errors use the AWS error body on both APIs, as Bedrock does, for example {"__type":"ThrottlingException","message":"..."} for a 429.

The dashboard shows Bedrock Converse and InvokeModel traffic as Bedrock, with the messages, reply and token counts. InvokeModel calls to models other than Claude and Nova (for example Llama or Titan) are labelled Bedrock but show no reply or token counts.

 

Streaming Responses

Set streaming to true on the completion to return a stream instead of a single JSON response. MockServer splits the text into token-sized chunks and sends them as streaming chunks in the provider's native streaming format (SSE for most providers; NDJSON for Ollama; binary AWS event-stream for Bedrock). Gemini follows the request, as the real API does: a streamGenerateContent request with ?alt=sse gets SSE, and one without it gets a single JSON array of response chunks (application/json), which is what Google's REST client libraries expect.

By default the text is split into fine, subword-sized chunks that closely match how a real provider streams tokens (so a streamed response emits more, smaller deltas). Set subwordStreaming to false in streamingPhysics if you prefer the coarser whole-word chunking (one chunk per word). The timing controls below behave identically in both modes — subword chunking simply produces more deltas, which makes the overall stream take slightly longer at the same tokensPerSecond rate.

Use streamingPhysics to control timing — useful for testing loading indicators, timeouts, and backpressure handling: 

{
  "httpRequest": {
    "method": "POST",
    "path": "/v1/chat/completions"
  },
  "httpLlmResponse": {
    "provider": "OPENAI",
    "model": "gpt-4o",
    "completion": {
      "text": "This response is streamed token by token.",
      "streaming": true,
      "streamingPhysics": {
        "timeToFirstToken": {
          "timeUnit": "MILLISECONDS",
          "value": 200
        },
        "tokensPerSecond": 50,
        "jitter": 0.1,
        "seed": 42
      },
      "usage": {
        "inputTokens": 10,
        "outputTokens": 8
      }
    }
  }
}
FieldDescription
timeToFirstTokenDelay before the first SSE event is sent
tokensPerSecondBase token emission rate (1 – 10000)
jitterFractional uniform deviation from the base rate (0.0 – 1.0)
seedPRNG seed for reproducible inter-token timing
subwordStreamingWhether to stream fine subword-sized deltas (true, the default) or coarser whole-word deltas (false). Subword deltas are closer to a real provider's per-token stream

Token usage in an OpenAI stream. For OPENAI, AZURE_OPENAI, DEEPSEEK, XAI and ORCAROUTER, a stream carries the usage above only when the request asks for it, as the real APIs do. Three providers send it without being asked, as their real APIs do: MISTRAL puts usage on the chunk with the finish_reason, GROQ puts it in x_groq.usage on that chunk, and OPENROUTER always ends the stream with the usage chunk shown below, though its usage chunk has one choice with an empty delta that repeats the finish_reason, as OpenRouter's does, where OpenAI's has none. Some AI SDKs ask by default (the Vercel AI SDK does); in LangChain set stream_usage, and with the OpenAI SDKs pass stream_options. The request sets stream_options: 

{
  "model": "gpt-4o",
  "stream": true,
  "stream_options": { "include_usage": true },
  "messages": [{ "role": "user", "content": "Hello" }]
}

Every chunk then carries "usage": null, and one extra chunk with an empty choices array and the token counts comes just before [DONE]: 

data: {"id":"chatcmpl-...","object":"chat.completion.chunk","created":1759478400,"model":"gpt-4o","choices":[{"index":0,"delta":{},"finish_reason":"stop"}],"usage":null}

data: {"id":"chatcmpl-...","object":"chat.completion.chunk","created":1759478400,"model":"gpt-4o","choices":[],"usage":{"prompt_tokens":10,"completion_tokens":8,"total_tokens":18}}

data: [DONE]

Without include_usage no chunk has a usage field. A non-streaming response always includes usage.

 

Tool Calls

To mock an LLM response that invokes tools (function calling), add toolCalls to the completion: 

{
  "httpRequest": {
    "method": "POST",
    "path": "/v1/chat/completions"
  },
  "httpLlmResponse": {
    "provider": "OPENAI",
    "model": "gpt-4o",
    "completion": {
      "toolCalls": [
        {
          "id": "call_abc123",
          "name": "get_weather",
          "arguments": "{\"location\": \"London\"}"
        }
      ],
      "stopReason": "tool_use"
    }
  }
}

A tool call's id is returned as the tool-call id your client sends back with the tool result: tool_calls[].id for OpenAI and the OpenAI-compatible providers, the tool_use block's id for Anthropic and Bedrock, call_id for the OpenAI Responses API, toolUseId for the Bedrock Converse API, and functionCall.id for Gemini and tool_calls[].id for Ollama. Leave it out and MockServer generates one in the provider's format (Gemini and Ollama then send none, as their APIs allow).

For OpenAI-compatible mocks you can also set toolChoice on the completion to model the request's tool_choice directive. It accepts auto, none, required, or a named tool. When toolChoice is required and a tool call is configured, the mocked response's finish_reason is forced to tool_calls (for both non-streaming and streaming responses), matching how OpenAI behaves when a caller forces a tool call. Omitting toolChoice leaves the finish reason behaviour unchanged. 

{
  "httpLlmResponse": {
    "provider": "OPENAI",
    "model": "gpt-4o",
    "completion": {
      "toolChoice": "required",
      "toolCalls": [
        { "name": "get_weather", "arguments": "{\"location\": \"London\"}" }
      ]
    }
  }
}

With the OPENAI_RESPONSES provider, each tool call is returned as a function_call output item with an item id (fc_…) and a separate call_id (call_…), as the real Responses API does. If you set an id on the tool call, such as call_abc123 above, that becomes the call_id. Your agent sends the tool's result back as a function_call_output carrying that call_id, and that is what containsToolResultFor matches on. This also works when the next request sends only the result plus previous_response_id, whether or not the earlier turn was streamed. When streaming, the arguments arrive as response.function_call_arguments.delta events, and the final response.completed event carries the whole response, including its output. The OpenAI Agents SDK reads each turn from that event.

The streamed arguments are split into small pieces the same way text is, one delta event per piece, and each event is paced by tokensPerSecond when you set streaming physics. A streamed tool call with long arguments therefore takes longer with OPENAI_RESPONSES than with the other providers, which send a tool call's arguments in one piece.

 

Embeddings

Mock an embeddings endpoint by setting embedding instead of completion. MockServer returns a provider-correct embeddings response with a vector of the requested size. Set deterministicFromInput to true so the same input text always produces the same (L2-normalised) vector — ideal for reproducible tests of retrieval / vector-search code.

When deterministicFromInput is true, the vector is also semantically plausible: it is derived from the words and character n-grams in the input text, so texts that share vocabulary get a higher cosine similarity and unrelated texts are near-orthogonal. This means your retrieval / RAG code can rank related documents above unrelated ones offline — for example "the cat sat on the mat" scores far higher against "a cat sits on a mat" than against "quarterly financial report" — with no real embedding model and deterministic results for the same input, seed, and dimensions. 

{
  "httpRequest": {
    "method": "POST",
    "path": "/v1/embeddings"
  },
  "httpLlmResponse": {
    "provider": "OPENAI",
    "model": "text-embedding-3-small",
    "embedding": {
      "dimensions": 1536,
      "deterministicFromInput": true,
      "seed": 42
    }
  }
}

MockServer reads each provider's own input field and returns one vector per input, in the order sent, so a batch of documents gets a batch of vectors. With deterministicFromInput, the same text gets the same vector in every request and on every provider, as long as the seed and dimensions match.

MockServer rejects an embedding request that is over a limit with a 400 in the provider's own error format. Some of the limits are the provider's own, which the real API enforces too: the Titan and Cohere sizes and embedding types, 96 Cohere texts or inputs, and 2,048 OpenAI inputs. The rest are MockServer's own limits, which keep its responses small: 8,192 dimensions, 2,048 Gemini requests or Ollama inputs, and the total number of vector values. A request is rejected when:

  • the request asks for more than 8,192 dimensions, or for a size that is not a positive whole number;
  • the request asks for a size the provider does not offer: Titan Text Embeddings V2 dimensions must be 256, 512 or 1024, Titan Multimodal embeddingConfig.outputEmbeddingLength 256, 384 or 1024, and Cohere Embed v4 output_dimension 256, 512, 1024 or 1536;
  • the request has more than 2,048 inputs (Gemini requests), or more than 96 Cohere texts or inputs;
  • the request asks for a Cohere embedding_types or Titan embeddingTypes value the provider does not have;
  • the response would hold more than 262,144 vector values in total (inputs × dimensions, and × the number of Cohere embedding types), for example 171 inputs at 1,536 dimensions. An OpenAI-style request with "encoding_format":"base64", which the OpenAI SDKs send by default, may hold four times as many, 1,048,576 (682 inputs at 1,536 dimensions), because a base64 value is about a quarter of the size;
  • with deterministicFromInput, an input is longer than 1,048,576 characters (building a vector from text uses memory in proportion to its length; random vectors have no such limit). This is more than any real embedding provider accepts in one input, so it only stops oversized test data.

These limits keep the largest embedding response at about 5.6 MB, so a small request cannot make MockServer build a very large one. If a test needs a bigger batch, raise the configuration property llmEmbeddingMaxResponseValues (for example to 384000 for a LangChain batch of 1,000 inputs at 1,536 dimensions), send the batch in several requests, or set a smaller dimensions on the expectation: 2,048 inputs fit at 128 dimensions. For longer inputs, raise llmEmbeddingMaxInputCharacters.

ANTHROPIC and OPENAI_RESPONSES have no embeddings endpoint and return an error if used for an embedding mock.

 

Rerank

Mock a rerank endpoint by setting rerank with the COHERE or VOYAGE provider. MockServer reads the candidate documents from the request body's documents array and returns one result per document — each with its original index and a relevance_score — sorted from most to least relevant. Set deterministicFromInput to true so the same documents always score the same way. MockServer returns as many results as the request asks for (Cohere top_n, Voyage top_k); set topN on the expectation to override that. 

{
  "httpRequest": {
    "method": "POST",
    "path": "/v1/rerank"
  },
  "httpLlmResponse": {
    "provider": "COHERE",
    "rerank": {
      "topN": 3,
      "deterministicFromInput": true,
      "seed": 42
    }
  }
}

Each provider returns its own response envelope around the same per-document scores ({"index": N, "relevance_score": F}), sorted by descending relevance:

ProviderResponse shape
COHERE{"results": [{"index": 1, "relevance_score": 0.9123}, ...], "id": "...", "meta": {"api_version": {"version": "2"}, "billed_units": {"search_units": 1}}}. Multimodal Request Recognition (Images and Audio)

When matching against requests, MockServer recognises image and audio content parts in the decoded conversation, so conversation predicates can assert that a message contained an image or an audio clip (and, where the provider declares it, the media type or audio format). For the OpenAI-compatible format this covers image_url and input_audio content parts. This is request-side recognition only — MockServer notes the presence (and how many) but does not store the media bytes or generate image/audio responses.

For agent testing, you often need to script a sequence of LLM responses that depend on what the agent sent. MockServer supports this through conversation predicates combined with scenario state to create multi-turn conversation flows.

Each turn uses conversationPredicates to match against the conversation history in the request body, and scenario state to track which turn the conversation is on: 

[

        "turnIndex": 0,
        "latestMessageContains": "weather"

  {
    "httpRequest": {
      "method": "POST",
      "path": "/v1/chat/completions"

Conversation predicates

Predicates match against the parsed conversation in the request body (decoded using the provider's message format):

PredicateDescription
turnIndexMatch when the assistant turn count equals this value (0-based)
latestMessageContainsMatch when the last message contains this substring
latestMessageMatchesMatch when the last message matches this regex pattern
latestMessageRoleMatch when the last message has this role (e.g. user, tool)

}
 

Session Isolation

When multiple agents or test threads share a MockServer instance, each conversation needs its own independent state. Use an isolation source to extract a session key from each request (a header, query parameter, or cookie) so conversation state is tracked per session.

Session isolation is configured via the Java client’s conversation builder (isolateBy(IsolationSource.header("x-session-id"))) or the create_llm_conversation MCP tool’s isolateBy parameter. The isolation source is encoded into the expectation’s scenario name — it is not a separate field in the raw expectation JSON. Common isolation sources:

  • Header: extract the session key from a request header (e.g. x-session-id)
  • Query parameter: extract from a URL query parameter
  • Cookie: extract from a cookie value

Example using the create_llm_conversation MCP tool:

{
  "provider": "OPENAI",
  "path": "/v1/chat/completions",
  "isolateBy": {
    "source": "header",
    "name": "x-session-id"
  },
  "turns": [
    {
      "match": { "turnIndex": 0 },
      "response": { "text": "Hello!", "stopReason": "stop" }
    }
  ]
}

Each unique isolation key value creates an independent conversation state machine, so multiple agents can run conversations in parallel without interfering with each other.

 

Realtime Voice APIs (OpenAI Realtime, Gemini Live)

The realtime voice APIs — the OpenAI Realtime API and the Google Gemini Live API — are not ordinary HTTP calls: the client opens a WebSocket and exchanges a stream of JSON events. MockServer can mock both so you can test an agent or app that uses them completely offline, with no real API, no cost, and no audio hardware. The mock replies to the client’s control messages with the provider-correct event stream for one scripted spoken turn (transcript deltas, audio-byte deltas, and a final usage/done event).

Point your realtime SDK at MockServer’s WebSocket URL (e.g. ws://localhost:1080/v1/realtime) instead of the real provider. Audio bytes in the mocked stream are short silence placeholders — the aim is to reproduce the event protocol faithfully (so your event-handling code is exercised), not to synthesise real speech. The same scripted turn answers every request on the connection.

Available in the Java client only. Realtime voice mocking is a Java-client convenience (RealtimeMockBuilder): there is no dedicated realtime JSON field. The builder expands the short script below into a full provider-correct httpWebSocketResponse expectation (session events, streamed transcript/audio deltas, and a final usage event) using the server-side realtime codecs. Reproducing that by hand in another client would mean writing out every WebSocket frame, so the other client libraries do not offer this shortcut. 

import static org.mockserver.client.RealtimeMockBuilder.openAiRealtime;
import static org.mockserver.llm.realtime.RealtimeTurn.realtimeTurn;

// Mock a spoken response over ws://localhost:1080/v1/realtime
openAiRealtime()
    .withModel("gpt-realtime")
    .respondingWith(
        realtimeTurn("The capital of France is Paris.")
            .withInputTokens(20)
            .withOutputTokens(7)
    )
    .applyTo(mockServerClient);

// On connect the mock pushes session.created; it acknowledges session.update and
// conversation.item.create, and answers each response.create with the full event
// lifecycle ending in response.done (with usage).
import static org.mockserver.client.RealtimeMockBuilder.geminiLive;

// Mock a Gemini Live BidiGenerateContent session
geminiLive()
    .respondingWith("Bonjour le monde")
    .applyTo(mockServerClient);

// The mock answers the client's setup message with setupComplete, then answers each
// clientContent turn with a streamed serverContent chunk sequence, generationComplete,
// and a final turnComplete carrying usageMetadata.

Use .withModality(RealtimeModality.TEXT) for a text-only response, .withTokensPerSecond(...) / .withTimeToFirstToken(...) to control streaming timing, and .respondingWith(realtimeTurn(...)) to set an explicit transcript, synthetic audio bytes, or token usage. Protocol corners that are intentionally not mocked yet (server voice-activity-detection events, tool/function calls, input-audio transcription) are listed in the developer documentation.

 

Cost Budget

When using MockServer as a proxy in front of a real LLM provider, the llmCostBudgetUsd property sets a cumulative cost ceiling. Once the estimated cost of all forwarded LLM completions exceeds the budget, further LLM forwards are blocked with a 429 response. This is a safety net for CI pipelines or development environments where runaway agents could generate unexpected charges.

PropertyEnv varDefaultDescription
mockserver.llmCostBudgetUsd MOCKSERVER_LLM_COST_BUDGET_USD -1.0 (disabled) Cumulative cost budget in USD. Set to a positive value to enable; negative or unset means no limit.

The budget is enforced on all forward paths (matched forward actions, proxy-pass, and reverse-proxy routes) and resets on PUT /mockserver/reset. Cost estimation uses an internal pricing table and is approximate — treat it as a safety guard, not an invoice.

Streamed responses are counted too. MockServer reads the token usage the provider reports in the stream and adds the call's cost when the stream ends. The budget is checked before each call is forwarded, so a call that is already streaming when the budget is reached still completes and the next one is blocked. MockServer never estimates usage: a stream that reports none is not counted, and MockServer logs a warning naming the provider and model (no token usage in the streamed ... response, at most once a minute for each provider and model), so check that your client asks for usage where the provider needs it:

ProviderUsage in a streamed response
OpenAI Chat Completions, Azure OpenAI Chat Completions Only when the client asks for it. Set "stream_options": {"include_usage": true} in the request (most SDKs and agent frameworks have a setting for this). Without it the call is not counted towards the budget.
OpenAI Responses API Always sent, in the final response.completed event. Nothing to set.
Anthropic Always sent. If the stream is cut off part-way, the input tokens and the output tokens reported up to that point are counted.
Gemini Always sent, on every chunk. Nothing to set.
AWS Bedrock Always sent by ConverseStream, for every model. The price comes from the model named in the request path, including a cross-Region inference profile such as us.anthropic.claude-...; only Anthropic Claude models have a price, so other models are counted in tokens only. For InvokeModelWithResponseStream only Anthropic models are counted; streams from other model families (Nova, Titan, Llama, Mistral) are not counted.
Mistral, OpenRouter, Groq Sent without being asked for. Nothing to set.
Other OpenAI-compatible providers If the provider follows OpenAI, set stream_options.include_usage as above.
Ollama Always sent. Local models have no cost, so they are counted in tokens only.

Calls through proxyPassMappings reverse-proxy routes are counted the same way, by the host the mapping forwards to. Only calls to a model are counted: completions, and whole embeddings and rerank responses, whose trace spans are named embeddings <model> and rerank <model> instead of chat <model>. An OpenAI response created with background: true and an xAI deferred completion report their usage only when the finished result is fetched, so that fetch is counted, once however many times it is polled. Other requests to an LLM host, such as listing models, fetching an ordinary stored response, counting tokens or Ollama's /api/pull download progress, are relayed but not treated as an LLM call. Behind a gateway or private endpoint that is not a known provider host, set llmProvider so Gemini and Bedrock calls through it are recognised and counted.

 

Moderation, Content Filter & Refusal

Production agents must handle provider content-filter blocks and refusals. These opt-in fields let you trigger them deterministically. All default to off / not-flagged, so existing mocks are unaffected.

OpenAI Moderations endpoint — set moderation (instead of completion) and a request returns OpenAI's /v1/moderations shape. Categories listed in flaggedCategories are marked flagged; an empty list is a not-flagged verdict. 

{
  "httpRequest": {
    "method": "POST",
    "path": "/v1/moderations"
  },
  "httpLlmResponse": {
    "provider": "OPENAI",
    "moderation": {
      "flaggedCategories": [ "hate", "violence" ]
    }
  }
}

Azure content-filter annotations — set contentFilter with per-category severities (hate, sexual, violence, selfHarm: one of safe, low, medium, high) on an AZURE_OPENAI completion. MockServer adds the content_filter_results (per choice) and prompt_filter_results (top-level) annotations agents read to detect filtering (filtered is true at medium/high). 

{
  "httpRequest": {
    "method": "POST",
    "path": "/openai/deployments/gpt-4o/chat/completions"
  },
  "httpLlmResponse": {
    "provider": "AZURE_OPENAI",
    "model": "gpt-4o",
    "completion": { "text": "Filtered response" },
    "contentFilter": { "hate": "high", "violence": "safe" }
  }
}

Refusals & content-filter blocks — an Anthropic refusal is just a completion with "stopReason": "refusal". As the real API does, every Anthropic refusal (whole or streamed, including one returned through Bedrock InvokeModel) carries a stop_details object, {"type": "refusal", "category": null, "explanation": null}; a stream carries it in the message_delta event's delta, so SDK code that reads stop_details works against the mock. To inject a block probabilistically across providers, use the contentFilterBlockProbability chaos field (see below), which emits the provider-correct shape.

org.mockserver.model.Usage has three optional fields in addition to the baseline inputTokens / outputTokens pair. These are back-compatible and optional: omitting them leaves the response without the matching provider fields. The one exception is OPENAI_RESPONSES, which always returns usage.input_tokens_details and usage.output_tokens_details, as the real Responses API does, with 0 for each count you do not set.

These examples show how to create a streaming LLM expectation with realistic timing physics. The Java client uses the typed fluent API; all other clients send the expectation as raw JSON. 

import static java.util.concurrent.TimeUnit.MILLISECONDS;

import static org.mockserver.client.Llm.tokensPerSecond;
import static org.mockserver.client.LlmMockBuilder.llmMock;
import static org.mockserver.model.Completion.completion;
import static org.mockserver.model.Provider.OPENAI;

llmMock("/v1/chat/completions")
    .withProvider(OPENAI)
    .withModel("gpt-4o")
    .respondingWith(
        completion()
            .withText("This response is streamed token by token.")
            .streaming()
            .withStreamingPhysics(
                timeToFirstToken(200, MILLISECONDS),
                tokensPerSecond(50),
                jitter(0.1))
